# larva-patterns

The Twig + JS prototype pattern library. The `larva` pattern server renders it, and every brand theme consumes it, as Twig through the server and as PHP partials generated by `twig-to-php-parser` (`packages/twig-to-php-parser/AGENTS.md`).
Depends on larva-css, larva-js, larva-svg and `lodash.clonedeep`. There are no unit tests for patterns (root `jest.config.js` ignores `/larva-patterns/`); they are checked by preview and visual regression.

## Read before editing

- Read `.agents/rules/larva-twig-templates.md` before editing any `*.twig` file here. Twig variable names decide escaping in the generated PHP, and only a small Twig subset is supported.
- Read `.agents/rules/larva-pattern-data.md` before editing any pattern data `*.js` file (`<name>.prototype.js` and variants).

Codex gets no generated rule view, so these pointers are how it finds the rules.

## Anatomy

- One directory per pattern: `<type>/<name>/` containing `<name>.twig`, `<name>.prototype.js` (default data), optional `<name>.<variant>.js` (variant data) and an optional `README.md`.
- Type prefixes: components `c-` (`components/`), objects `o-` (`objects/`), modules unprefixed (`modules/`), algorithms `a-` (`algorithms/`, `.html` + `.prototype.js`, no `.twig`).
- The prefix is load-bearing: `twig-to-php-parser` maps `c-` → `components`, `o-` → `objects`, and unprefixed names → `modules` (`packages/twig-to-php-parser/lib/twig-to-php-parser.php:261-266`).
- The server loads data from `<type>/<name>/<name>.<variant>.js`, with the variant defaulting to `prototype` (`packages/larva/lib/utils/getPatternData.js:9-16`). A differently named data file is never found.
- Each pattern's `README.md` is rendered as its docs page; without one the server shows "This needs docs!".
- Composition: modules include objects and components; objects include components. Includes use the `@larva` Twig namespace (`@project` is a consuming project's own patterns).
- `__tests__/<page>/` holds the full-page compositions (`profile`, `profile-index`, `vlanding`, `css`, `hub`) that backstop screenshots (`larva.config.js:13`). They are used only for visual regression.
- `_data/`, `_templates/`, `style-guide/` and `utils/` support the pattern server UI.
- `index.js` exports only the `o_nav` and `o_tease` prototypes; consumers reach other patterns by path.
- `README.md` in this directory is an empty skeleton. Link per-pattern READMEs instead.

## Conventions

- Preview with `npm run larva` from the root and open `http://localhost:3000/larva/<type>/<name>` or `…/<name>/<variant>` (route `/:source/:type/:name/:variant?`).
- Styling comes from larva-css classes (`lrv-u-*` utilities, `lrv-a-*` algorithms). If a needed class does not exist, add it in `packages/larva-css`. Do not write pattern-local CSS here.
- Behavior comes from larva-js. Use the `js-*`, `lrv-js-*` or `data-*` hook that the target larva-js module queries.
- Data files and templates must agree on variable names.
- `.html` files (the server UI shell `base.html`, `pattern.html`, `index.html`, `css.html`, plus `style-guide/`, `_templates/`, the `__tests__` backstop pages and the algorithm demos) are rendered only by Twing in the preview server. They are never converted to PHP and may use full Twig.
- Changing a pattern used by the five `__tests__` pages changes screenshots. If the change is intended, update references through the approval workflow (`approval.yml`), never locally.
- Patterns ship to every brand theme, and data keys are a public API: themes and the PMC Larva PHP plugin (`\PMC\Larva\Pattern::render_pattern_template`) pass data with these keys. Renaming or removing a key breaks consumers and belongs in `UPGRADING.md`.

Preferred default for new modules: the root element opens with `class="<name> // {{ <name>_classes }} …"` (64 of 105 modules; consumer backstop configs select modules by `.<name>`). Components and objects follow their neighbors (`class="c-<name> … {{ c_<name>_classes }}"`).

Avoid:

- `modules/foo/foo.js` or `modules/foo/data.js`: the server only loads `foo.prototype.js` and `foo.<variant>.js`.
- Omitting `c-` on a component or `o-` on an object: the PHP parser routes generated include calls by name prefix, so the include points at `modules/`. Module names are unprefixed by convention.
- Using `{% set %}` or `{% elseif %}` in a PHP-bound `.twig` pattern.

## Adding a pattern

1. Create `<type>/<name>/` with `<name>.twig` and `<name>.prototype.js`. Add a `README.md` describing usage.
2. Compose children with `{% include "@larva/<type>/<child>/<child>.twig" with <child_data> %}` and cloned child data.
3. Preview at `http://localhost:3000/larva/<type>/<name>` (and `/<variant>` for each variant).
4. Run `npm test` and `npm run lint` from the root, and read the lint output.
5. Run `npm run prod` from the root and commit any generated diffs.
6. Add a `## Unpublished Changes` line in `CHANGELOG.md`: `* larva-patterns - Add <name> module.`
7. In the PR, include a screenshot and the Vercel preview link (`PULL_REQUEST_TEMPLATE.md`).

A new variant is one `<name>.<variant>.js` file, plus the CHANGELOG line and any rebuilt output.
